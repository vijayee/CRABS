## HIGH

### A10-1. `oabe_cp_ct_deserialize` returns SUCCESS with NULL output — HIGH, conf 9
`deps/openabe-c/src/utils/oabe_ciphertext.c:470-474,524,540-542`. Three bounds checks (`policy_len` vs remaining bytes, `num_components > 4096`, `attr_len` cap/overrun) `goto error` **without setting `rc`**, which is still `OABE_SUCCESS` from the preceding `unpack32`. The error label frees the ciphertext, sets `*ct = NULL`, and `return rc;` — success with a NULL output. Caller `oabe_context_cp_decrypt` (`deps/openabe-c/src/abe/oabe_context.c:1245-1251`) checks only `rc != OABE_SUCCESS` and then dereferences `ct->policy` — a **reliable NULL-deref DoS from any crafted CP-ABE ciphertext blob**, reachable through `crypto_abe_decrypt` (src/Crypto/crypto.c:1124). Fix: set `rc = OABE_ERROR_INVALID_CIPHERTEXT` before each unchecked `goto error`.

### A10-2. Heap over-read in `oabe_secret_key_deserialize` — HIGH, conf 8
`deps/openabe-c/src/keys/oabe_key.c:930-992`. After `unpack32` of `alpha_len`, `beta_len`, `id_len`, and `key_data_len`, the code does `oabe_bytestring_new_from_data(input + index, len)` / `memcpy(..., id_len)` with **no `index + len <= input->size` check** (the checked helper `unpack_with_len` exists but is bypassed). A crafted MSK blob (accepted by `crypto_master_key_deserialize` via `oabe_context_cp_set_secret_key`, crypto.c:1001) yields a heap over-read of up to 4 GiB — segfault DoS, with over-read bytes copied into `key_id`/`key_data`. CRABS's own `_restore_msk_scalars` (crypto.c:877-942) parses the same envelope *with* correct bounds checks, but the vulnerable openabe-c parse runs first, so the mitigation does not protect this path.

### A10-3. Heap over-read in `oabe_user_key_deserialize` — HIGH, conf 8
`deps/openabe-c/src/keys/oabe_key.c:1186-1268`. Identical unchecked-length pattern for `id_len`, `attr_len`, `policy_len`, `key_data_len`. Reachable via `crypto_abe_decrypt` → `oabe_context_cp_import_key` with a crafted user-key blob. Same impact as A10-2.

### A10-4. Unchecked `elem_len` in `deserialize_cp_key_elements` — HIGH, conf 8
`deps/openabe-c/src/abe/oabe_context.c:188-207`. After `unpack32(&elem_len)` there is no bound check before `oabe_bytestring_new_from_data(data_ptr + index, elem_len)`. Crafted key bytes imported via `oabe_context_cp_import_key` cause a heap over-read of up to 4 GiB. Additionally, `elem_len == 0` `continue`s without appending, so a declared `count` can deserialize to a shorter vector; the downstream `oabe_vector_get` returns NULL so that fails closed, but the count/shape mismatch is unvalidated.

### A10-5. Lineage resident-registry/manifest index misalignment across restart — HIGH, conf 8
`src/Lineage/lineage.c:993-1003` (`_lineage_register_resident_child` appends at `resident_child_count`) vs. `lineage.c:1170-1202` (manifest appended at `child_count`). The comment at :990-992 asserts both arrays "only ever append at the tail in the same order," but v11 persists the manifest (serialization.c:1578-1588) while `resident_child_count` resets to 0 on load — no code rebuilds the registry. A post-restart spawn of child D puts D at registry slot 0 with manifest index N≥1. Consequences: `lineage_query_resident_child(old_child)` returns D (wrong-machine borrow into JS/N-API wrappers); `lineage_op_dissolve` on an old child (`lineage.c:1402-1406`) sets `lineage_parent_dissolved = true` on **D** (wrongful in-process severance) and NULLs D's slot; dissolve of D itself fails the `child_index < resident_child_count` bound at :970, so D is never severed in-process and **keeps authorizing `@parent/` endorsements with pre-issued attestations until TTL expiry or tombstone delivery** — violating the spec's instant-void invariant. Triggered by an ordinary restart → `machine spawn` → `machine dissolve` op sequence. Fix: rebuild the runtime registry with hole-aware indexing on load, or key resident slots by child id rather than positional index.

### A10-6. Write-after-free in `lineage_op_dissolve` via dangling resident slot — HIGH, conf 7
`src/Lineage/lineage.c:1402-1404`. Registry slots are explicitly UNOWNED, and `data_model.h:431-447` documents that a caller destroying a child out-of-band "leaves a dangling entry" while claiming lookups "never dereference" such slots. That is false for dissolve: `_lineage_find_resident_child` returns the dangling pointer and the handler writes `resident->base_state.lineage_parent_dissolved = true` through it. `lineage.h:213-214` grants the spawn caller destroy ownership, making spawn → owner destroys child → any `role:admin` signer executes `__dissolve_machine__` a documented-usage trigger for a **heap write-after-free**. The node binding mitigates by retaining all spawned children for the parent's lifetime (`crabs_node.cc:1473`), but wasm and other owners can violate the contract. (A second auditor independently confirmed this at lower severity rating; kept HIGH given memory-safety class.) Fix: drop the slot on child destroy, or store a weak-liveness token.

### A10-7. CLI `key import` command does not exist; the shipped binary is single-shot — HIGH (operational), conf 9
Two halves of one finding. (a) `src/CLI/cli.c:2398-2419`: the `key` dispatcher wires only `generate`, `refresh`, `revoke`, yet four messages direct the operator to "run 'key import' with the node private key" (cli.c:296, 400, 499); `cli_node_load_key` (cli.c:380) — the only function that can verify the pending snapshot signature and clear `state_sig_pending` — has **no dispatch wiring**. Every load of a signed snapshot leaves `state_sig_pending=true` forever, so `cli_node_save` (cli.c:496) refuses unconditionally. (b) `src/CLI/main.c:9-20` creates a fresh `cli_node_t`, dispatches exactly one command, and destroys the node; `cli_node_save` requires `node->initialized`, which only `init`/`load`/`load-sealed` set — in the *same* process. So `crabs_node save` always fails, `seal-key import` imports into a node destroyed at exit, and `state accept-unverified`'s acknowledgment is discarded at exit. **The entire load→mutate→save authenticated-durability flow is dead in the shipped binary** and is exercised only by the in-process test harness (`test/test_cli.cpp`). Any operator believing they have authenticated at-rest backups via the CLI does not.

### A10-8. Signed snapshot fully adopted before its signature is ever verified — HIGH (operational, same root as A10-7), conf 7
`cli.c:268-299` strips the 64-byte trailer, parses, and adopts the entire state (policies, config, user registry, lineage bindings, MSK unseal) with no ECDSA check, deferring verification to the unwired `cli_node_load_key`. This generalizes the Audit-9 "unsigned state loads on warning" gap: the *signed* path is parse-then-maybe-verify, and in the CLI binary the "maybe" is never. Fields are trusted (state adopted at cli.c:348) prior to any authentication.

## MEDIUM

- **A10-M1. Trigger `CHANGE_POLICY` can rewrite lineage-op policies** (conf 7) — `src/Trigger/trigger.c:131-151`, `state_machine.c:2189`, `lineage.c:1465-1469`. The H-E guard blocks `CHANGE_POLICY` effects only when `operation_is_builtin()` is true, but the `CRABS_LINEAGE_OP_*` names are absent from that table (verified: state_machine.c:209's builtin list has no lineage entries; lineage ops are handler-registered "custom" ops with a default `role:admin` policy installed by `lineage_install`). A trigger creator with `__create_trigger__` authority can install a trigger that replaces the `__spawn_machine__`/`__dissolve_machine__`/`__revoke_attestation__` policy with any non-empty ABE expression they satisfy, silently bypassing admin gating of the lineage lifecycle. The same omission lets `__define_operation_type__` attach signer-chosen dedup guards/mutations to lineage op types. Fix: extend the builtin check (or both guards) to cover the lineage op names.
- **A10-M2. Mode B primary signer can double as co-signer** (conf 6) — `state_machine.c:885-928`. `_verify_co_signatures` rejects `cs->signer_id == op->signer_id`, but in Mode B `op->signer_id` is empty, so the comparison never matches the *resolved* primary signer (held in `resolved_signer` but never passed in). The comment quotes v1.3 §4.2 ("co-signers must be distinct … from the primary signer"), yet a Mode B proposer can occupy one of the N co-signer slots, collapsing "proposer + N distinct approvers" to N-1 distinct additional approvers.
- **A10-M3. Null `node_key_` deref in N-API `CreateTrigger`** (conf 9, crash-only) — `bindings/node/src/crabs_node.cc:1366` dereferences `node_key_->private_key` unconditionally; adopted child wrappers (from `lineageSpawn`/`lineageResidentChild`, ctor at :699-709) set `node_key_ = nullptr`, so `childWrapper.createTrigger({...})` segfaults. `crabs_serialize_for_signing`'s NULL return is also unchecked (:1365). Same crash class in any adopted-wrapper method touching `node_key_` without the guard `GetNodeKey` has (:979).
- **A10-M4. Listener-vector invalidation during `EmitChange`** (conf 7) — `crabs_node.cc:790-797` iterates `change_listeners_` by reference while a listener callback runs synchronously; a listener that calls `node.on('change', …)` triggers `push_back` (:844), reallocating the vector and leaving the range-for holding freed heap. Reachable from pure JS; heap UAF on `FunctionReference` objects.
- **A10-M5. Parent retains cryptographic admin custody of "sovereign" children** (conf 7, docs/spec gap) — `lineage.c:1121-1122`: DELEGATED_COPY/SOVEREIGN genesis runs `attribute_machine_create(blueprint->bootstrap_admin, parent->node_public_key)` — the child's genesis `role:admin` user is keyed by the *parent's* node key, and no handover/rotation is required at spawn. The parent can sign arbitrary admin ops on a sovereign child indefinitely (policy changes, new users, its own tombstone acceptance), contradicting README ("Sovereign children are beyond parent control") and the spec's "full sovereignty" profile. Sovereignty exists only after a cooperative rotation performed with the parent's key; the trust-model docs should state this.
- **A10-M6. `lineage_parent_public_key` pinned at spawn, no rotation path** (conf 6) — `lineage.c:1134` copies the parent's node key into the child permanently; endorsements and tombstones verify only against it (state_machine.c:688, lineage.c:1622). Node keys are freely re-set (cli.c:365/442, `state_set_node_key`), so a parent re-key permanently orphans every child's lineage (legitimate attestations/tombstones fail), and a compromised *old* key retains forge capability over every child spawned under it. The spec's `parent_key_chain` field that would have addressed this was dropped without replacement.
- **A10-M7. Ordered-set duplicate-id rejection is O(n²) under a 1M-element cap** (conf 6) — `serialization.c:468-482`: the Audit-9 fix rejects duplicate element ids with a linear scan per element; the count cap stays `CRABS_DESER_MAX_LOG` (1M). Audit 8 capped OT-tree nodes at 10,000 for exactly this quadratic-scan DoS; the ordered-set sibling was not capped the same way. A ~120 MB crafted blob can drive ~10¹² op-id comparisons. Fix: remaining-buffer/118 bound and/or hash-set dedup.
- **A10-M8. `machine` lineage subcommands missing from unauthenticated-snapshot warning list** (conf 8, audit-visibility only) — `_warn_first_unauthenticated_mutation` (cli.c:1943-1964) enumerates item add, policy add, compact, user (non-list), key refresh/revoke, op submit/define — but not the new `machine` subcommands (spawn, attest, tombstone, dissolve, revoke-attestation). Lineage mutations on an unauthenticated snapshot run silently; the hard save-gate remains, so impact is audit-visibility only.

## LOW

- **A10-L6. No full-consumption check in state deserialization** (conf 5) — `_deserialize_state_internal` returns without verifying `buf.offset` exhausts the payload (op deserialization enforces this at serialization.c:2618). Fail-closed (only downgrades which warning fires).
- **A10-L7. - **A10-L8. State file written without permission restriction** (conf 6) — cli.c:536 `fopen(path, "wb")` under default umask; no 0600/chmod. Blob is signed and MSK AEAD-sealed, so exposure is ciphertext + metadata, but restrictive permissions would be defense in depth.

- **A10-L10. Quote-blind endorsement extraction rewrites quoted literals** (conf 4) — `_extract_parent_endorsements` (condition.c:1375-1485) scans raw text without tracking quoted regions; `members CONTAINS "@parent/x"` becomes endorsement `x` plus `CONTAINS ""`. - **A10-L14. `lineage_spawn_machine` N-API binding bypasses the policy-gated op path** (conf 8, INFO) — binding calls the C function directly (no op, no policy check, no log entry); the signed `__spawn_machine__` op path is the audited one. ## Verified clean this round

**crypto.c core** (full re-read): ECDSA low-S normalization on sign and reject on verify; secp256k1 private-key range validation (`_eckey_from_private`); public-key on-curve/not-infinity validation at registration *and* at both ECIES directions (N-3, R5-6, R7-L-3); MSK cleansed on all destroy/deserialize paths (N-17); per-authority key-ID sequence (N-9); keystore key removal on export failure (R8-C-8); empty-policy fail-closed with signature-still-required semantics (N-4); user-existence/status error collapsing (R7-14, R8-C-6); sig-and-policy evaluated jointly before combining (R7-L-8); legacy bootstrap key rejected once a keyring exists (R8-C-2); key-status + key-expiry enforcement on both key-resolution paths; co-signer policy satisfaction (R7-L-9); envelope signing covers the ECIES-encrypted sk_abe (encrypt-then-sign); envelope/user-id NUL forced on deserialize (R8-C-9); key rotation validates new key before any mutation (R7-06, R8-C-3); seal/unseal AEAD with tag-before-plaintext.

**sig_scheme registry:** linear lookup (no scheme-indexed array), duplicate-ID rejection, fail-closed NULL dispatch, builtin vtable enforces pk_len/sig_len/sk_len before use; no trivial-verify path.

**openabe-c DEM:** fresh random 96-bit GCM nonce per encryption; per-ciphertext unique key, tag enforced before plaintext release, symkey cleansed on all paths; error codes distinct without leaking tamper-vs-policy.

**Tombstone & attestation protocol:** canonical bodies (tag+string16, exact body-length consumption); `child_id` matched to `lineage_self_id` before signature cost; verify against persisted parent key; unbound-machine and replay refusals fail closed; endorsement anchors `parent_id` and `user_id == resolved_signer`; Mode B anonymous ops rejected for endorsement policies; TTL overflow checked; deserializer rejects over-long strings, wrong prefix lengths, trailing bytes, over-cap counts.

**Spawn lifecycle:** blueprint validated before allocation; genesis hash recomputed and compared; child_id uniqueness across manifest/self-id/bootstrap_admin; registry-before-manifest with rollback (no partial residue); shared-root MSK borrow honored in both destroy paths; honest-tombstone gate; sovereign non-dissolvable; reload without `lineage_install` fails loudly (4443fdb).

**Authorization ordering** (state_machine.c:930-1248): auth → tx-accept → HLC → replay-monotonicity → transitions → lock claims → dedup → key-version/scheme/co-sig gates → handler → log → version++ → tx commit; no op mutates without a verified signature; the only `skip_authorization` path (scheduled materialization) was validated at submission.

**Bindings hygiene:** every byte-returning export uses `Napi::Buffer::Copy` (no aliasing); spawn reveals only the parent *public* key as child genesis admin pk; no JS/wasm path exposes node private key, MSK, or user ABE keys; child-wrapper lifetime (adopted + parent keepalive) is double-free-safe.
