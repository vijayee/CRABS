## High

### A11-1. `oabe_params_deserialize` still trusts all length prefixes (fork) — HIGH, conf 8
`deps/openabe-c/src/keys/oabe_key.c:~555-735` (first hole ~:599; g1/g2/gt/g1_alpha/egg_alpha/g1_a/g2_a/key_data blocks). Commit 9da0a04 fixed this exact bug class in the secret-key, user-key, and key-elements deserializers but MISSED the params deserializer: every `if (X_len > 0) { oabe_bytestring_new_from_data(ptr + index, X_len); ... }` has no `index + X_len > size` check — a crafted params blob over-reads the heap by up to 4 GiB per field. Reachable from CRABS via `oabe_context_cp_set_public_params` (oabe_context.c:695, 1626), i.e. through `crypto_master_key_deserialize` and the encryptor path — the same trust boundary as the fixed A10-2/3/4 blobs. Fix: same bounds-check pattern as 9da0a04.

## Medium

### A11-2. REPL tokenization has no quoting; spaced policy expressions silently truncate — MEDIUM (policy weakening), conf 9
`src/CLI/cli.c:2650` — `cli_cmd_policy_add(node, argv[3], argv[4])` ignores `argv[5+]`. The shell REPL (A10-7b) tokenizes on whitespace with no quoting support, so an operator typing `policy add myop role:admin OR role:member` (legal spec syntax, Protocol v1.3 Am3 §558) installs the TRUNCATED policy `role:admin` with no error, and confirmations print only the truncated form. Single-shot argv was protected by the invoking shell collapsing quoted spaces; the REPL makes silent truncation the default. A silently-weakened policy is an authorization-weakening footgun. Fix: either reject surplus argv in mutating subcommands that take a final "expression" argument (join argv[4..] with spaces after validating none of the pieces are quoted-intent), or add quoting to the REPL tokenizer and reject unbalanced quotes; minimum: warn loudly on surplus tokens.

### A11-3. Zero-length MSK scalars now fail OPEN in the fork (regression vs deleted `_restore_msk_scalars`) — MEDIUM, conf 8
`deps/openabe-c/src/keys/oabe_key.c:~956, ~979`: alpha/beta reconstruction is skipped when `alpha_len == 0`/`beta_len == 0`, returning `OABE_SUCCESS` with NULL scalars. The deleted CRABS-side `_restore_msk_scalars` failed closed on empty scalars (zp_deserialize of an empty slice errors). Downstream, `oabe_context_cp_keygen` calls `oabe_g2_mul_scalar(K, ..., secret_key->alpha)` (~:793) and `oabe_zp_mul(beta_t, ..., beta)` (~:806) and `oabe_zp_clone(alpha)` (:1610, :1801) with return values unchecked — a malformed/tampered MSK blob with zeroed scalar lengths mints silently-degenerate user keys instead of erroring. Fix: reject `alpha_len == 0 || beta_len == 0` in `oabe_secret_key_deserialize` (and ideally assert the reconstructed scalars non-NULL in `oabe_context_cp_keygen`).

### A11-4. Retired lineage keys retain live authority, not "historical" — trust-model doc gap — MEDIUM (docs), conf 9
`src/Lineage/lineage.c:2180-2195` (`lineage_verify_by_parent_key`) and ~:215-235 (`attestation_verify_by_lineage_key`) verify against EVERY chain entry with no temporal qualifier, and tombstones carry no time component (`lineage_op_receive_dissolution` ~:1858). So a compromised retired parent key can mint FRESH attestations (not_before=now) and sign dissolution tombstones for any child of that parent at any time — permanent authority until the chain fills/refuses. Only chain advancement is tip-gated (474b184). README:~223 describes retired keys as valid "for verifying historical attestations and tombstones," which understates this. This was the designed backward-compat posture (Task 11: any chain key verifies; tip-only was applied to chain ADVANCEMENT only, per the final-review decision), but per the project's trust-model rule the README must state the real residual authority, and/or the chain verify should distinguish: verify-by-tip for NEW attestations (option to gate fresh-window attestations on the tip key) — a design decision for the next round's remediation.

### A11-5. Double-rotate without key installation permanently wedges the chain — MEDIUM (operational), conf 7
`src/Lineage/lineage.c:1960-2046`: `lineage_key_rotate` bumps the parent's `lineage_key_version` and stashes a new record regardless of whether the previous rotation's key was installed via `state_set_node_key`. After two unstalled rotations the stashed record's `old_pk` is the still-installed ORIGINAL key while children sit at version 2: tip-gate rejects forever, and the parent's version counter gap-rejects all subsequent records. Self-inflicted (admin API misuse, not attacker-reachable), but recoveryless in-band. Fix options: refuse rotate while `new_public_key != state_set_node_key`-installed tip of the PREVIOUS rotation is unconfirmed (track installed-version), or document loudly + provide a lineage reset. Minimum: refuse `lineage_key_rotate` when the parent's node public key != the last rotation's `new_pk` but version already advanced (i.e., detect the wedge and fail with a clear error instead of silently stacking).

## Low

- **A11-L1. Single-slot stash makes >1-behind children uncatchable** (conf 8, lineage.c ~:2037-2041) — restart re-emits only the LAST transition; a child that missed two rotations gap-rejects and the intermediate record is unrecoverable (retired private key gone). By design; document the operational precondition (deliver each rotation before minting the next, or retain every transition record).
- **A11-L2. `_lineage_key_transition_write_body` writes trailing `created_at` without a cap check** (conf 8, lineage.c ~:1955) — overflow only if `cap ∈ (BODY_MIN, BODY_MIN+8)` with a max-length parent_id; the sole caller passes BODY_MAX where the layout lands exactly. Latent fragility; the doc comment's "0 when cap is too small" is not universally true.
- **A11-L3. `strlen(parent_id)` unguarded on hand-built states** (conf 8, lineage.c ~:1952) — reads a fixed `char[64]` field without strnlen discipline; deserialized states are terminated, so caller-bug-only, but the surrounding code guards this exact case uniformly.
- **A11-L4. Registry holes never compact** (conf 10, lineage.c:1128) — NULLed slots persist and `resident_child_count` grows one pointer per lifetime spawn (8 B each). Cosmetic.

- **A11-L7. Cleanse-on-throw incomplete at hex-decode failures** (conf 6, crabs_node.cc ~:634-635, ~:1364-1365) — the ser-failure throws cleanse `priv`, the decode-failure throws don't (contents = prefix of caller-supplied key bytes; negligible, but inconsistent with the stated hygiene goal).
